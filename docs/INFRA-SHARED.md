# البنية التحتية المشتركة — Medify وpickly على خادم واحد

> مصدر الحقيقة لكل ما يتعلق بمشاركة الخادم. حُرِّر 2026-08-03 بعد عطل انقطاع الدومين.

## الحقيقة الأساسية

Medify يعمل على **خادم Oracle مشترك** مع مشروع آخر (pickly) — `VM.Standard.A1.Flex`،
4 vCPU · 24GB RAM · قرص 49GB، وهو **سقف الطبقة المجانية الدائمة** بالضبط.

القاعدة الملزمة من المالك: **أي عمل على Medify يجب ألا يمسّ pickly**.

## ما هو معزول فعلاً (تُحقّق منه 2026-08-03)

| الطبقة | pickly | Medify |
|---|---|---|
| مشروع compose | `vm-*` (11 حاوية) | `medify-prod` · `medify-staging` |
| شبكة Docker | `vm_default` | `medify-prod_default` · `medify-staging_default` |
| قاعدة البيانات | `vm_pgdata` | `medify-prod_pgdata` · `medify-staging_pgdata` |
| المنافذ | 80 · 443 · 3000-3004 · 4000 | 8080/8444 · 8090/8445 · 8081 (الهبوط) |
| الكود على الخادم | `/home/ubuntu/pickly` | `/opt/medify/src` |
| الأسرار | داخل مشروع pickly | `/opt/medify/.env` |

**صفر شبكة مشتركة · صفر فوليوم مشترك · صفر تداخل منافذ.** لا يستطيع أي طرف قراءة
قاعدة الآخر.

## الاعتماد المُعلَن: بوابة الدخول

المنفذان **80/443 يملكهما `vm-caddy`** (بروكسي pickly). كل زوّار `medifysa.co` يمرّون
به ثم يُحوَّلون إلى `172.18.0.1:8080` عبر جسر المضيف — لا عبر شبكة مشتركة.

**نتيجته:** سقوط `vm-caddy` يُسقط دومين Medify (التطبيق يبقى حياً على المنفذ 8080
مباشرة). ولذلك يُعامَل `vm-caddy` كمكوّن ذي إتاحة أعلى من المشروعين معاً.

### نموذج الملكية (بعد إصلاح 2026-08-03)

الملف الرئيسي لـ`vm-caddy` **متتبَّع في git الخاص بـpickly**، ونشره الذاتي
(`pickly-autodeploy.timer`) يشغّل `git reset --hard origin/main` **كل دقيقتين** —
فأي تعديل يدوي عليه ممحوّ حتماً. هذا سبب انقطاعي 2026-07-27 و2026-08-03.

الحل المطبَّق: ملف pickly يحوي **سطراً ثابتاً واحداً** لا يتغير:

```
import /data/conf.d/*.caddyfile
```

وشظية Medify تعيش في `/data/conf.d/medifysa.caddyfile` (داخل فوليوم `vm_caddydata`
المركّب أصلاً على `/data`)، ومصدر حقيقتها **هذا المستودع**:
[`infra/deploy/medifysa.caddyfile`](../infra/deploy/medifysa.caddyfile).

للتحديث: عدّل الشظية هنا ثم `bash infra/deploy/sync-caddy.sh` — يرفع، يفحص
`caddy validate`، يعيد التحميل ذرياً، ويتحقق من الاستجابة. **لا تحرّر ملف pickly.**

> لماذا فوليوم قائم بدل bind mount جديد: إضافة mount تستلزم تعديل
> `infra/vm/docker-compose.prod.yml` في pickly، وهو مسار «كود مشترك» في نشره
> الذاتي فيُعيد بناء خدماته السبع كلها. بهذا الشكل: صفر إعادة بناء.

## الموارد المشتركة والحراسة

- **القرص** (49GB، مشترك): كاش بناء Docker هو المفترس الأكبر — بلغ 24GB في
  2026-08-03. الحارس `infra/deploy/disk-guard.sh` مركّب على `/opt/medify/bin/`
  بـcron يومي 04:00 UTC: يقلّم كاش البناء والصور المعلّقة فقط عند تجاوز 85%،
  وتقليماً كاملاً عند 92%. **لا يمسّ حاوية ولا فوليوم لأي مشروع.**
- **الذاكرة** (24GB): لحاويات Medify سقوف في `infra/docker-compose.prod.yml`
  (`deploy.resources.limits`) — حارس ضد الجموح لا ضبط أداء.
- **السجلات**: `max-size: 10m` × 3 ملفات لكل حاوية Medify. تسري على الحاويات
  المُنشأة بعد التعديل فقط ⇒ يلزم `up -d` لا `restart`.
- **ملاحظة على الطبقات**: صور المشروعين تتشارك طبقات أساسية (node · postgres ·
  redis · python) تُخزَّن مرة واحدة. لذلك **تقسيم القرص إلى قسمين يزيد الاستهلاك
  ولا ينقصه**، ويلغي مرونة تقاسم الفراغ. لو لزمت مساحة: أضف block volume ثانياً.

## المراقبة

`.github/workflows/uptime.yml` — كل 30 دقيقة من خارج البنية: الجذر · `/login` ·
`/api/v1/health` · تحويل `www` · مصافحة TLS وصلاحية الشهادة ≥ 10 أيام. الفشل
يُرسل بريداً تلقائياً من GitHub. **الفحص من خارج الخادم عمداً** — فحصٌ يعمل على
الخادم نفسه أعمى عن سقوط الخادم.

## متى يُفصل المشروعان فعلياً

الفصل الكامل قرار **تجاري لا هندسي**: Medify يحمل بيانات مرضى، ومراجعات أمن
المعلومات في المستشفيات تسأل عمّن يشارك الخادم. الجواب التقني اليوم سليم (عزل
كامل للشبكة والبيانات) لكنه ثقيل في اجتماع تعاقد. المحفّز المقترح: أول عقد
مستشفى حقيقي.

الطريق حينها: حصة الطبقة المجانية تقبل التقسيم على عدة نسخ A1 — خادم مستقل
لـMedify بـ2 vCPU/12GB بصفر كلفة إضافية، مقابل تنصيف الموارد وعملية ترحيل.

## أوامر تشخيص سريعة

```bash
# هل يعرف caddy دومين Medify؟ (غيابه = سبب ERR_SSL_PROTOCOL_ERROR)
docker logs vm-caddy-1 2>&1 | grep -o "medifysa[^\"]*" | tail -3
# هل الشظية في مكانها؟
docker exec vm-caddy-1 ls -la /data/conf.d/
# آخر ما فعله نشر pickly الذاتي
tail -20 /home/ubuntu/pickly-autodeploy.log
# المساحة وما يمكن استرداده
docker system df
```
